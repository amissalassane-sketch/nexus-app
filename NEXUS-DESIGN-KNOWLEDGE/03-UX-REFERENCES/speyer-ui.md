# Speyer UI — principes retenus pour NEXUS

Source : dépôt open source `speyer-ui` ("SUI"), design system qui se présente comme traitant "l'accessibilité comme de l'architecture, pas comme un après-coup". Analysé en lecture (README, section Accessibility), jamais republié tel quel.

## Ce qui est transférable

- **L'accessibilité vérifiée par un script automatique avant chaque build, pas seulement par une checklist humaine.** SUI fait tourner 66 vérifications automatiques (contraste sur 40+ paires de tokens dans les deux thèmes, 15 règles axe-core dont `button-name`/`link-name`/`heading-order`, cohérence de version) avant de publier. **C'est l'écart le plus concret entre SUI et NEXUS** : NEXUS a des règles d'accessibilité très complètes et déjà mesurées à la main dans les commentaires de `globals.css` (contrastes calculés en commentaire "DESIGN AUDIT"), mais `ANALYSIS-REPORT.md` confirme qu'il n'existe **aucun framework de test de composants (Jest/Vitest/Playwright)** dans le projet — la vérification reste humaine et manuelle à chaque changement. Recommandation concrète : ajouter un script de vérification automatique (axe-core + Playwright, ou une bibliothèque de contraste sur les paires de tokens de `globals.css`) qui échoue le build si une règle déjà documentée dans `NEXUS-DESIGN-RULES.md` est violée. Voir aussi `07-DESIGN-INTELLIGENCE/accessibility-standards.md` pour la checklist existante, qui devient le cahier des charges de ce script.
- **Le statut n'est jamais porté par la couleur seule — toujours couleur + icône + texte.** Règle déjà appliquée par NEXUS via `StatusDot` (documenté dans `NEXUS-COMPONENTS.md`) — SUI confirme que c'est la bonne discipline par convergence externe.
- **Cible tactile minimale de 44px, chiffrée et non négociable.** NEXUS a déjà une distinction desktop/tactile dans son échelle de bouton (`h-9`/`sm:h-8` par exemple), mais la valeur plancher de 44px n'est pas citée comme seuil explicite dans `NEXUS-DESIGN-RULES.md`. À vérifier : les tailles `xs`/`icon` les plus petites de `button.tsx` (`h-7`, `w-7`/`h-8`/`w-8` en desktop) tombent sous 44px sur des écrans tactiles si elles ne sont jamais servies qu'en contexte desktop réel (`sm:` les réduit, donc elles ne s'appliquent qu'au-delà du breakpoint tactile) — cohérent en l'état, mais vaut la peine d'ajouter le seuil 44px comme règle explicite plutôt qu'implicite dans les valeurs choisies.
- **`<dialog>` natif pour les modales, pour déléguer le piège de focus au navigateur.** SUI utilise l'élément HTML natif plutôt qu'une réimplémentation, précisément pour ne pas avoir à coder à la main la gestion de focus. Le `Modal` de NEXUS (`src/components/ui/modal.tsx`) restitue déjà le focus à la fermeture et gère `Escape`, mais **ne boucle pas le `Tab`** à l'intérieur du panneau (pas de piège de focus actif) — un utilisateur clavier peut sortir de la modale par Tab avant de la fermer. C'est un vrai écart avec les bonnes pratiques de modale, indépendamment de cette référence. Deux options : migrer vers `<dialog>` natif (gain : le navigateur gère le piège de focus gratuitement), ou ajouter un piège de focus manuel dans l'effet existant. Les deux sont hors du scope des correctifs déjà appliqués dans cette session (voir le rapport d'audit) faute de pouvoir compiler/tester le changement ici.

## Ce qu'on NE prend PAS

- Les 538 icônes propres à SUI ni son sprite SVG — NEXUS utilise déjà `lucide-react` + `simple-icons`, pas de raison de changer de fournisseur d'icônes.
- L'absence de dépendance runtime et la distribution CDN — NEXUS est une app Next.js avec build, pas une bibliothèque zero-dependency distribuée par CDN ; le contexte de distribution diffère trop pour que ce choix soit transférable tel quel.
